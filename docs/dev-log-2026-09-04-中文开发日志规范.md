# 开发日志：建立中文开发日志规范

- 日期：2026-09-04
- 范围：仓库开发规则与 `docs/` 文档

## 目标

让以后每个开发任务在准备提交完成时，都在 `docs/` 留下一份独立的中文报告。报告需要保留实际开发现场的时间线和判断逻辑，方便事后按因果关系复盘，而不是只看到最终提交结果。

完成标准是：仓库长期规则明确要求写日志；提供统一模板；本次任务本身按新规则留下第一份日志。

## 时间线

1. 用户提出初始要求：每次任务准备提交完成时，在 `docs/` 记录整个开发现场的时间线和逻辑链条，报告必须使用中文。
2. 当时唯一会改变落地方式的缺口，是“每个任务单独成文”还是“所有任务追加到同一文件”。因此只针对这一点向用户确认，没有继续扩展格式要求。
3. 用户选择每个任务单独一个文件。
4. 开始落地前检查了仓库规则、与日志和任务完成相关的既有经验、工作树、分支和 worktree 状态。现场处于指向 `origin/main` 的分离头状态，工作树干净；本地 `main` 与拉取后的 `origin/main` 一致。
5. 按仓库规则先进入 Nix 开发环境，再从最新 `origin/main` 创建独立任务分支 `docs/chinese-development-logs`。
6. 决定采用“长期规则 + 可复制模板 + 本次真实日志”的最小方案：规则保证以后必须执行，模板保证报告结构稳定，本日志验证规则能够实际使用。
7. 在 `AGENTS.md` 增加“开发日志”规则，在 `docs/dev-log-_template.md` 增加中文模板，并创建本文件作为首份任务日志。
8. 完成后检查文件内容、Git 差异、模板章节和日志命名，确认改动只覆盖本任务范围。

## 逻辑链条

- 用户真正需要的是事后能够还原“为什么这样做”，所以日志必须同时包含时间线和决策依据；只有文件列表或提交摘要不能满足目标。
- 用户已确认“一任务一文件”，因此采用 `docs/dev-log-YYYY-MM-DD-<短任务名>.md`，避免不同任务互相混杂，也便于按日期和任务检索。
- 规则属于长期、跨任务且会约束后续行为的内容，所以写入 `AGENTS.md`；报告实例和模板属于项目文档，所以放在 `docs/`。
- 模板保留目标、时间线、逻辑链条、改动、验证和遗留六部分。这些部分覆盖了“做什么、经历什么、为什么、改了什么、如何证明、还有什么问题”的完整复盘链条。
- 没有采用脚本、Git 钩子或 CI 强制检查，因为用户目前只要求形成记录习惯；增加自动化会引入尚未被要求的复杂度。
- 没有补写历史任务日志，因为历史现场无法从当前事实中完整还原，补写容易把推测伪装成事实。

## 改动

- `AGENTS.md`：新增强制性的开发日志规则、命名方式、内容要求和生效边界。
- `docs/dev-log-_template.md`：新增每次任务可复用的中文日志模板。
- `docs/dev-log-2026-09-04-中文开发日志规范.md`：记录本次任务的实际过程，作为规则生效后的第一份日志。

本次改动不改变程序运行行为，也不修改已有的 `docs/` 文档。

## 验证

- 确认工作基于拉取后的最新 `origin/main` 创建独立分支。
- 检查模板包含目标、时间线、逻辑链条、改动、验证和遗留章节。
- 检查规则明确约束：每个开发任务、准备提交完成时、独立文件、位于 `docs/`、全文中文、缺少日志不算完成。
- 检查首份日志文件名符合约定，并按真实发生顺序记录了需求确认、现场检查、方案选择和改动过程。
- 检查 Git 差异，确保没有覆盖或回退无关改动。

## 遗留

- 当前没有用脚本、Git 钩子或 CI 自动检查日志是否存在；执行依赖后续任务遵守 `AGENTS.md`。
- 模板细节可在实际使用中调整，但调整时仍需保持中文、独立文件、真实时间线和逻辑链条这些已确认的核心要求。
